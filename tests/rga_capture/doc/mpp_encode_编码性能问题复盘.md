# mpp_encode 编码性能问题复盘记录

> 工程：`mediaCam/tests/mpp_encode`（RK3568 + IMX415 + rkisp_v5）
> 方案：V4L2 采集（MMAP）→ `VIDIOC_EXPBUF` 导出 dma-buf fd → `mpp_buffer_import` → MPP 硬件编码 H.264（零拷贝，对应官方文档图表17"纯外部分配"思路）
> 记录时间：2026-10-19

---

## 一、问题现象（先后出现三个）

### 现象1：一瞬间完成 600 帧，但输出只有 1 帧

```
encode 600 frames done!          ← 打印得极快
mpp encoder deinit, total 1 frames
```

**原因**：`encode_frame()` 里的 `printf(...)` 和 `return` 缩进对了，但**写在 for 循环体内部**：

```c
for (i = 0; i < frame_num; i++) {
    ...DQBUF / 编码 / QBUF...
    printf("encode %d frames done!\n", frame_num);   // ← 在循环体内
    return;                                          // ← 在循环体内
}
```

第 1 帧做完就直接 return，所以"瞬间完成"其实只跑了 1 次循环。

**修复**：把 `printf` + `return` 移到 for 循环之外。

**教训**：日志文案要和实际语义一致；"完成 600 帧"这种话在只跑了 1 次循环时也照打，极具误导性。

---

### 现象2：4K（3840×2160）播放卡顿

`ffplay -f h264 -framerate 30 imx415.h264` 观感一顿一顿。

实测：

| 项目 | 数值 |
|---|---|
| 600 帧耗时 | `real 0m45.264s` |
| 实际编码速度 | 600 ÷ 45.264 = **13.25 fps** |
| 文件帧数（ffprobe） | 600（帧数没少，但内容时间跨度是 45 秒） |
| 摄像头实际帧率 | 时间戳间隔 **40ms → 25fps** |

**判断**：文件被标成 600 帧 @30fps = 20 秒，但真实内容跨了 45 秒 → 播放时既加速又跳帧。RK3568 编码器标称 1080p@60，4K 属于超规格，硬件吞吐只有二十帧上下。

---

### 现象3：降到 1080p 仍只有 15.4fps，而且程序退出前莫名卡 14 秒

1080p 实测仍不理想：

| 项目 | 数值 |
|---|---|
| 600 帧耗时 | `real 0m39.038s` → 15.4fps |
| `user` CPU 时间 | 14.7s（异常高） |

**关键推理**：4K 13.25fps → 1080p 15.4fps，**分辨率降了 4 倍速度却几乎没变**，说明瓶颈不是像素吞吐，而是"每帧固定开销"或"循环之外的开销"。

---

## 二、定位过程（靠分段计时，不靠猜）

在关键路径插入 `clock_gettime`，把一段一段耗时拆开。

### 第 1 轮：拆开单帧内部的三个阶段

`mpp_encoder_encode_fd()` 内部分别计时：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| `mpp_buffer_import` | **65 µs** | 导入 dma-buf，极快，不是瓶颈 |
| `encode_put_frame` | **13~15 ms** | 硬件编码真实开销 |
| `encode_get_packet` | **0.6~0.9 ms** | 取码流，很快 |
| `dqbuf`（外层采集等待） | **22~25 ms** | 在正常等下一帧 |

单帧合计 ≈ **37ms → 约 25~27fps**，并且 **和摄像头 25fps 完全匹配（满帧、不丢帧）**。

### 第 2 轮：发现 20 帧总共只花 0.78 秒，但 real 却是 15.8 秒

| 阶段 | 耗时 |
|---|---|
| `mpp_encoder_init` | 37 ms |
| `encode_frame(20)` | 778 ms |
| `mpp_encoder_deinit` | 12 ms |
| **合计** | **≈ 0.83 s** |
| **`real`** | **15.843 s** |
| `user` | **13.948 s** ← 纯用户态 CPU 空转 |

差值 ≈ 14 秒，且几乎全是 user CPU，说明有一段**纯软件空转**，与硬件无关。

### 第 3 轮：A/B 验证是不是进程退出时的库清理

- 在 `close_device()` 前后计时：**7 ms**（排除）
- 在 `return 0;` 前加 `_exit(0);`（跳过所有 atexit / 全局析构）：

```
real 1.906s     user 0.045s     sys 0.178s
```

14 秒消失，user 从 13.9s 掉到 0.045s。

## 三、结论

### 1. 编码链路本身是达标的

1080p 下：`dqbuf 23ms + 编码 13.5ms + 取包 0.7ms ≈ 37ms` → **稳定 25fps，与 IMX415 25fps 完全匹配，零丢帧**。
`import 65µs` 说明**外部 dma-buf 零拷贝导入几乎没有成本**，"模式三"方案本身是成功的。

### 2. 那 14 秒是 `librockchip_mpp` 退出时的全局清理在空转

- 不在 `close_device`，不在 `mpp_destroy`（deinit 只有 12ms），而在**进程退出阶段库的析构 / 线程 join**；
- 属于库自身问题，与业务代码无关；
- 正式产品是常驻进程，不会走退出路径，因此**测试程序里用 `_exit(0)` 规避即可**；
- 注意：`_exit` 不刷新 stdio 缓冲，但 `mpp_encoder_deinit()` 内已 `fclose(fp_out)`，h264 文件是完整的。

### 3. 4K 是硬件规格问题，不是代码问题

RK3568 编码器标称 1080p@60。4K@25fps 采集下实际只有 ~20fps 编码能力：
- 想跑 4K：把 sensor 帧率降到 15~20fps，并让 `rc:fps_in/out` 与之对齐（`./mpp_encode 15`）；
- 想要流畅：用 1080p，这是该平台编码的最佳工况。

### 4. 播放"卡"还叠加了一个帧率标注问题

裸 H.264 没有时间戳，`ffplay` 完全依赖 `-framerate` 参数。内容 25fps 却用 `-framerate 30` 播，等于 1.2 倍速，观感必然怪。
**正确用法**：`./mpp_encode 25`（编码 25fps）+ `ffplay -framerate 25 imx415.h264`。

## 四、方法论沉淀

1. **`time` 是第一诊断工具**：`real` 和 `user` 的差值能立刻区分"等硬件"和"CPU 空转"。
2. **先算账再改代码**：`单帧耗时 × 帧数` 与 `real` 对不上，就一定存在未测量的开销，不要盲目优化。
3. **分辨率对照实验**：降 4 倍分辨率速度不变 → 排除像素吞吐，锁定固定开销。
4. **时间戳反推真实帧率**：`(ts_n - ts_0) / n` 就能知道摄像头到底多少 fps，不要相信 assumed 值（本次发现实际是 25fps 而非 30fps）。
5. **裸流播放必须对齐 `-framerate`**，否则会把"帧率标注错误"误判成"编码卡顿"。
6. **`_exit` 是定位"退出阶段卡顿"的利器**：能瞬间区分业务代码与库析构。
