# RGA 练习题：4K NV12 → 1080p 零拷贝缩放

> 位置：`tests/rga_capture/`
> 难度：★★☆☆☆（主线）／★★★☆☆（加餐）
> 预计：主线 1.5–2 小时，加餐 1 小时
> 前置：现有 `./mpp_encode 1` 能正常出流
> 目标：做完这道题，能独立讲清 RGA 的 **buffer / format / stride / rect / sync** 五件事

## 一、题目

现有链路是 **IMX415 4K NV12 → MPP 直接编码**。RK3568 的编码器是 1080p 规格，4K 直编只有 13–20fps，属于超规格使用。

请用 RGA 在采集和编码之间加一级缩放：

**主线（必做）**

实现一个 `rga_scale_test`：把一帧 **3840×2160 NV12** 缩放成 **1920×1080 NV12**，输入、输出都使用 **dma-buf fd**，结果保存为 `/root/rga_1080p.nv12`，并给出 100 次调用的平均耗时。

**加餐（选做）**

把这一级缩放接进现有 `V4L2 → MPP` 链路，编码 1080p H.264，端到端跑满 25fps。

**一句话验收**

```text
$ ./rga_scale_test
RGA: rga_api version 1.10.0_[8]
src: 3840x2160 wstride=3840 hstride=2160 fmt=NV12
dst: 1920x1080 wstride=1920 hstride=1080 fmt=NV12
resize: 3.21 ms  (avg of 100: 2.84 ms, min 2.61, max 4.02)
saved /root/rga_1080p.nv12 (3110400 bytes)
```

并且：

- 文件能转成正确的 PNG，颜色、方向、比例都正常；
- 与 ffmpeg 参考缩放结果的 PSNR ≥ 28dB；
- 循环 100 次前后，进程 fd 数不增长；
- `dmesg` 里没有 RGA 报错。

## 二、这道题练什么

| 知识点 | 在题里的体现 |
|---|---|
| `rga_buffer_t` 包装 | 把 V4L2 / dma-heap 的 fd 变成 RGA 能读写的 buffer |
| 像素格式 | NV12 对应 `RK_FORMAT_YCbCr_420_SP`，写错会红蓝互换 |
| stride | `wstride` 是行跨度，`hstride` 是垂直跨度；NV12 的 chroma 偏移是 `wstride * hstride` |
| 缩放 | `imresize` 全图缩放，理解目标尺寸与比例 |
| 裁剪（加餐） | `imcrop` 只取源图的一个矩形，理解 `im_rect` |
| 同步 | `sync=1` 阻塞等待；`sync=0` 拿 fence 做流水线 |
| 零拷贝 | 全程只传 fd，不做 CPU 像素搬运 |
| 性能 | 区分首帧开销、稳态耗时、带宽账 |

## 三、环境与构建

### 3.1 软件版本

| 项 | 值 |
|---|---|
| 芯片 | RK3568（RGA2） |
| librga | 2.1.0（`librga.so.2.1.0`） |
| im2d API | 1.10.0 |
| 头文件 | `$SYSROOT/usr/include/rga/` |
| 内核 | `CONFIG_DMABUF_HEAPS_SYSTEM=y`，无 ION |

`$SYSROOT` 指：

```text
/root/rk3568/rk3568_linux_sdk/buildroot/output/rockchip_atk_dlrk3568/host/aarch64-buildroot-linux-gnu/sysroot
```

### 3.2 构建注意

```make
CFLAGS += -I$(SYSROOT)/usr/include/rga
LDLIBS += -L$(SYSROOT)/usr/lib -l:librga.so.2.1.0
```

这个 sysroot 里 **只有 `librga.so.2.1.0`，没有 `librga.so` 开发软链**，所以 `-lrga` 很可能报
`cannot find -lrga`。用 `-l:librga.so.2.1.0`，或者自己补一个软链。

程序跑起来之前，顺手确认一下运行库的 SONAME：

```bash
readelf -d librga.so.2.1.0 | grep SONAME
```

如果 SONAME 是 `librga.so.2`，而板端 `/usr/lib` 下没有同名文件/软链，就在板端补一个，或者用
`LD_LIBRARY_PATH` 指向放好软链的目录。**编译通过 ≠ 板端能加载**，这一步先排掉。

### 3.3 设备节点

```bash
ls -l /dev/rga
ls -l /dev/dma_heap/
# 正常应看到 /dev/dma_heap/system，可能还有 /dev/dma_heap/cma
```

本内核没开 ION，`/dev/ion` 不存在是正常的，不要照着 ION 的旧例程找。

### 3.4 测试素材

在主机上生成一张确定性的 4K NV12 测试图，再传到板子：

```bash
ffmpeg -f lavfi -i testsrc2=size=3840x2160:rate=1 \
       -frames:v 1 -pix_fmt nv12 -f rawvideo src_4k.nv12

scp src_4k.nv12 root@<board>:/root/
```

`testsrc2` 有清晰的边缘和色块，stride 写错、色度平面错位都会非常明显。

## 四、任务分解

### M0　文件 → 文件（隔离变量，先跑通 RGA）

这一步**不碰摄像头**，只验证 RGA 本身。

1. 从 `/dev/dma_heap/system` 分配两块 dma-buf：
   - src：至少 `3840×2160×1.5` 字节；
   - dst：至少 `1920×1080×1.5` 字节。
2. `mmap` 后把 `src_4k.nv12` 读进 src 缓冲区（这一步允许 CPU 拷贝）。
3. 用 fd 包装成两个 `rga_buffer_t`，调用 `imresize`。
4. `mmap` dst，把结果写成 `rga_1080p.nv12`。
5. 打印：RGA 版本、源/目的宽高与 stride、返回状态、单次耗时。

**完成标准**

- 输出文件大小正好 `1920*1080*3/2 = 3,110,400` 字节；
- PNG 与源图内容一致，只是变小；没有斜切、没有底部绿边、没有红蓝互换；
- 失败时能看到 `imStrError()` 的具体原因，而不是只打印一个负数。

> 为什么 M0 就用 dma-buf，而不是先 `malloc` 再 `wrapbuffer_virtualaddr`？
> 因为最终链路一定要走 fd，直接用最终方案可以少写一版、少调一次。

### M1　摄像头 fd → dma-buf（去掉拷贝）

1. 复用 `v4l2_capture.c` 的采集流程，预热 20 帧后取 1 帧。
2. **不要 memcpy**，直接把 `dev->buffers[buf.index].fd` 包成 src。
3. 用 `VIDIOC_G_FMT` 读回真实几何信息，不要相信 `main.c` 里写死的 `3840×2160`：

   ```c
   struct v4l2_format fmt = {0};
   fmt.type = V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE;
   ioctl(dev->fd, VIDIOC_G_FMT, &fmt);
   /* mplane 用 fmt.fmt.pix_mp:
    *   width / height / num_planes
    *   plane_fmt[0].bytesperline  -> wstride
    *   plane_fmt[0].sizeimage     -> 缓冲区大小
    */
   ```

4. 把源帧和缩放帧都存下来，方便对比：
   - `/root/rga_src_4k.nv12`
   - `/root/rga_1080p.nv12`

**完成标准**

- 摄像头画面正确（可以先存一张 4K 源图确认采集本身没问题）；
- 缩放图与源图取景一致，没有左右错位、没有从中间开始斜；
- 日志里能看到实际的 `width/height/bytesperline/sizeimage`。

> 如果实际几何是 `3864×2192` 这类带对齐的值，不要惊讶。按实际值缩放即可；
> 想保持 16:9 就做中心裁剪（见加餐 A）。

### M2　100 次基准与资源稳定性

1. 先空跑 5 次预热（首帧会包含上下文/导入开销）。
2. 固定同一对 src/dst，循环 100 次，统计 min / avg / max。
3. 记录循环前后的 fd 数：

   ```bash
   ls /proc/self/fd | wc -l
   ```

4. 跑完 `dmesg | tail -30`，确认没有 RGA timeout / IOMMU fault。

**完成标准**

- 4K→1080p 单次平均 ≤ 10ms 为合格，≤ 5ms 为优秀；
- 100 次前后 fd 数一致；
- 能解释首帧为什么比稳态慢。

### M3　接回 MPP（加餐）

1. 把 M1 的缩放结果直接交给 `mpp_encoder_encode_fd()`，不要再落盘再读。
2. 编码器配置改成 `1920×1080`，`hor_stride/ver_stride` 与 RGA 输出一致，帧率 25。
3. 连续跑 10 秒，打印分段耗时：
   - `dqbuf` 等待
   - RGA
   - `encode_put_frame`
   - `encode_get_packet`
   - 端到端 fps

**完成标准**

- `ffprobe` 显示 1920×1080，时长约 10s；
- 端到端 ≥ 24fps，接近摄像头 25fps；
- RGA 单帧 ≤ 4ms，且不成为新瓶颈；
- 与 4K 直编对比，给出“改前/改后”的数字。

## 五、硬性约束

1. **零拷贝**：RGA 的 src 和 dst 都必须是 dma-buf fd；数据通路里不允许 `memcpy` 整帧，不允许 CPU 缩放。M0 装载/保存测试文件时的拷贝不算。
2. **用 im2d API**：`imresize` / `imcrop` / `imrotate` 等；不要用 legacy 的 `c_RkRgaBlit`。
3. **每个 `IM_STATUS` 都要检查**，失败打印 `imStrError(status)`。
4. **不许硬编码 3840/2160**：从 `VIDIOC_G_FMT` 或参数读取；目的尺寸可以配置。
5. **保存的 NV12 必须紧凑**：每行 `width` 像素。若 `wstride > width`，要按行打包后再写文件，否则播放器会斜。
6. **资源释放**：`munmap`、`close`、`releasebuffer_handle`（如果用了 handle）都要成对；100 次循环 fd 不增长。
7. **不破坏现有目标**：`make` 仍能产出原来的 `mpp_encode`。测试程序建议放 `test/` 或 `tools/` 下单独建 target；现有 Makefile 用 `src/*.c` 通配，再把一个 `main()` 丢进 `src/` 会出现重复 main。

## 七、提示（先自己做，卡住再看）

### 7.1 最小调用链

```c
#include "im2d.h"

/* 1. 拿 fd：dma_heap 分配，或 V4L2 EXPBUF，或 mpp_buffer_get_fd() */
/* 2. 包装：注意宏的参数顺序是 (fd, w, h, format, [wstride], [hstride]) */
rga_buffer_t src = wrapbuffer_fd(src_fd, src_w, src_h,
                                 RK_FORMAT_YCbCr_420_SP,
                                 src_wstride, src_hstride);

rga_buffer_t dst = wrapbuffer_fd(dst_fd, dst_w, dst_h,
                                 RK_FORMAT_YCbCr_420_SP,
                                 dst_wstride, dst_hstride);

/* 3. 缩放：两个参数版本表示 fx/fy 取 0，直接用 dst 的宽高 */
IM_STATUS ret = imresize(src, dst);
if (ret != IM_STATUS_SUCCESS) {
    printf("imresize failed: %s\n", imStrError(ret));
}
```

也可以直接调 C 函数，参数顺序和宏不同：

```c
rga_buffer_t src = wrapbuffer_fd_t(src_fd, src_w, src_h,
                                   src_wstride, src_hstride,
                                   RK_FORMAT_YCbCr_420_SP);
```

`wrapbuffer_fd` 是宏，`wrapbuffer_fd_t` 是函数，两者参数顺序不一样，别混。

### 7.2 dma_heap 分配

```c
#include <linux/dma-heap.h>

struct dma_heap_allocation_data data = {
    .len       = size,
    .fd_flags  = O_RDWR | O_CLOEXEC,
    .heap_flags = 0,
};

int heap_fd = open("/dev/dma_heap/system", O_RDWR | O_CLOEXEC);
ioctl(heap_fd, DMA_HEAP_IOCTL_ALLOC, &data);
/* data.fd 就是 dma-buf fd */
```

需要 CPU 访问时再 `mmap(data.fd, size, PROT_READ | PROT_WRITE, MAP_SHARED, 0)`。
CMA heap 用法一样，把路径换成 `/dev/dma_heap/cma` 即可；系统堆碎片多、性能异常时再试 CMA。

### 7.3 常见坑

| 现象 | 大概率原因 |
|---|---|
| 红蓝互换 | NV12 当成 NV21，或 `RK_FORMAT_YCrCb_420_SP` 用错 |
| 图像斜切 / 越往右越歪 | `wstride` 传成了 `width`，但实际 buffer 有对齐 |
| 下半部分绿 / 花 | chroma 平面偏移算错，`wstride*hstride` 不对，或 dst 缓冲区太小 |
| 只有上半截有图 | `hstride` 或 buffer size 不足 |
| `IM_STATUS_INVALID_PARAM` | 宽高为奇数、rect 越界、format 不支持 |
| `IM_STATUS_ERROR_VERSION` | 头文件与库版本不匹配（本环境一般不会） |
| 第一次特别慢 | 首次 import/上下文初始化；预热 5 次再统计 |
| 输出全灰/全绿 | resize 没真正执行，或 dst 根本没被写；先用 `imfill` 验证 dst 可写 |
| CPU 读出来是旧数据 | 用了 cached dma-buf，读写前后需要 `DMA_BUF_IOCTL_SYNC` |
| 程序退出卡十几秒 | MPP 库析构问题，测试程序用 `_exit(0)`（你之前已踩过） |

### 7.4 建议的调试顺序

1. 先 `imcopy` 同尺寸 1:1 复制，确认 fd 包装和读写通路没问题；
2. 再 `imfill` 把 dst 涂成已知值，确认 dst 能被 RGA 写；
3. 再做 4K→1080p `imresize`；
4. 每一步都存图，不要只靠 printf；
5. 跑的时候另开终端 `dmesg -w`，RGA 的错误通常直接打在这里。

## 十、加餐题（任选）

**A. 中心裁剪 + 缩放**

4K 是 16:9，若实际输出是 3864×2192（略高），直接整帧缩到 1920×1080 会轻微变形。
用 `imcrop` 先取中心 16:9 区域，再缩放到 1920×1080：

```c
im_rect rect = { .x = (w - crop_w) / 2, .y = (h - crop_h) / 2,
                 .width = crop_w, .height = crop_h };
imcrop(src, dst, rect);
```

对比“整帧缩放”和“裁剪后缩放”的取景差异。

**B. 旋转 90°**

把 3840×2160 转成 1080×1920 竖屏，再编码。注意 dst 的 `wstride/hstride` 和 MPP 的
`width/height/hor_stride/ver_stride` 全部要跟着变；旋转后宽高互换，最容易在这里写错。

**C. OSD 进度条**

用 `imfill` 在右下角画一个随帧号变长的进度条（比如每帧加 2 像素），叠在 1080p 图上再编码。
先搞清楚 YUV 下 `color` 的含义，再看 `imfill` 的 rect 坐标系。

**D. RGA 与编码 overlap**

`imresize(..., sync=0, &fence_fd)` 提交后立刻去取上一帧的编码 packet，用 fence 等待，
测量流水线化之后端到端 fps 的变化。这是从“会用”到“用好”的分界线。
