# 帧率与延迟统计

> 目标：运行预览脚本时能同时看到帧率和延迟，并且知道每个数字测的是哪一段。
> 相关实现：[RTMP 推流实现](RTMP推流实现.md)、[RTMP 预览操作](RTMP预览操作.md)

---

## 一、三条延迟口径

| 口径 | 公式 | 测得到什么 | 是否需要改码流/对时 |
|---|---|---|---|
| `cap2enc` | 编码完成 − 该帧 V4L2 采集时间戳 | 采集 + RGA + 等环形缓冲 + 编码 | 否 |
| `cap2file` | 落盘完成 − 采集时间戳 | 采集到写进 `.h264` 文件 | 否 |
| `cap2mux` | RTMP 发送返回 − 采集时间戳 | 采集到 FFmpeg 把 FLV tag 写进 socket | 否 |

- 三个口径都基于 `CLOCK_MONOTONIC`，板端自己就能算，**不需要和 PC 对时**；
- `cap2mux` 是常用指标：它包含板端整条流水线，但不含网络传输、服务器转发、预览端缓冲；
- 端到端（玻璃到玻璃）延迟当前**不测**，原因见第六节。

采样点：

```text
t0  V4L2 buf.timestamp（采集帧到达驱动）
t1  编码线程把该帧的码流包写进 packet_rb（编码完成）
t2  消费线程写完本地文件
t3  av_interleaved_write_frame 返回
```

`cap2enc = t1 - t0`、`cap2file = t2 - t0`、`cap2mux = t3 - t0`。

## 二、板端统计（默认 1 Hz，常开）

每秒往 stderr 打一行，例如：

```text
[stats] 12s cap=29.8 enc=29.7 sent=29.6 file=29.6 fps drop=0 rb_f=0% rb_p=9% br=5.62Mbps fw=5.62MB/s lat_mux p50=20.8ms p95=27.4ms max=44.9ms
```

| 字段 | 含义 |
|---|---|
| `cap` / `enc` / `sent` / `file` | 本秒采集 / 编码 / RTMP 发送 / 落盘 的速率（帧/秒） |
| `drop` | RTMP 累计丢帧（未连接、等 IDR、发送失败） |
| `rb_f` / `rb_p` | frame / packet 环形缓冲占用百分比 |
| `br` | 本秒 RTMP 实测码率（H.264 负载，不含 FLV 封装） |
| `fw` | 本秒落盘吞吐 |
| `lat_mux` / `lat_file` | 延迟窗口内（最近 300 个样本，30fps 约 10 秒）的 p50/p95/max |

延迟采样窗口的统计在退出时补全 p99：

```text
[stats] total 37.2s cap=1108 enc=1104 saved=1104 sent=1100 drop=4 file=392.31MB rtmp=391.02MB
[stats] lat_cap2enc  p50=3.1ms  p95=4.8ms  p99=6.2ms  max=12.0ms n=300
[stats] lat_cap2file p50=12.4ms p95=18.9ms p99=25.1ms max=41.3ms n=300
[stats] lat_cap2mux  p50=20.8ms p95=27.4ms p99=35.0ms max=44.9ms n=300
```

> 说明：窗口只保留最近 300 个样本，`n` 表示样本数；运行时间短于 10 秒时 `n` 会小于 300。

### 时间戳基准校验

首次采样会检查 `now - pts` 是否在合理范围（0 ~ 10 秒）。如果打印：

```text
[stats] V4L2 timestamp is not CLOCK_MONOTONIC based (pts=... now=...), latency disabled
```

说明该驱动的 `buf.timestamp` 不是单调时钟基准，此时帧率统计照常，延迟统计关闭。RK 平台默认是
`CLOCK_MONOTONIC`，正常不会出现。

## 三、预览端统计（解码 fps / 显示 fps）

状态栏实时显示：

```text
预览中  1920x1080  解码 29.9fps  显示 29.7fps
```

终端每秒打印一行：

```text
[preview] decode=29.9fps display=29.7fps
```

| 指标 | 含义 | 偏低说明 |
|---|---|---|
| 解码 fps | `cap.read()` 每秒成功取到的帧数 | 网络抖动、服务器转发慢、解码跟不上 |
| 显示 fps | `paintEvent` 每秒实际绘制的帧数 | GUI 渲染/缩放跟不上（WSLg 或 CPU 紧张） |

这两个值只反映**播放侧是否流畅**，不等于端到端延迟。预览端用 OpenCV 解码，拿不到流内
SEI 或可靠的 PTS，因此无法单独算出“画面从采集到显示用了多久”。

## 四、怎么看数据

| 现象 | 更可能的原因 |
|---|---|
| `cap` 明显低于 30 | 采集端：曝光时间过长、驱动丢帧、RGA 阻塞 |
| `cap` 正常但 `enc` 低 | 编码/RGA 耗时，或 frame 环写入被消费端拖住 |
| `sent` 低、`drop` 涨 | RTMP 连不上/断流、服务器慢、网络差（板端不会因此停采集） |
| `lat_mux` 持续上涨、`rb_p` 接近 100% | 消费线程被网络阻塞（背压），packet 环在堆积 |
| `lat_file` 偶发尖峰 | 写盘抖动（eMMC/文件系统），看 `max` 是否影响体验 |
| 板端 `sent` 正常、预览 `decode` 低 | 预览侧网络/解码问题，不是板端 |
| 预览 `decode` 正常、`display` 低 | GUI 渲染瓶颈，窗口越大越明显 |

`-or` 模式下先落盘、后推流：写盘抖动会直接体现在 `lat_mux` 的尾部（`p95`/`max`），
如果影响明显，可以把输出盘换成更快介质或降低分辨率。

## 五、上板核对步骤

1. 板端运行（边推边录）：

   ```bash
   ./rkCam -or rtmp://<Windows局域网IP>:1935/live/imx415 /root/imx415.h264
   ```

2. 观察每秒 `[stats]` 行：`cap` 应接近 30，`drop` 不应持续增长；
3. 同时看预览端状态栏和 `[preview]` 行，解码 fps 应接近 30；
4. `Ctrl-C` 退出，检查汇总里的 `cap2mux` p95 是否稳定；
5. 用 `ffprobe` 或播放器核对落盘文件时长/帧数是否与 `saved` 一致：

   ```bash
   ffprobe -v error -count_frames -select_streams v:0 \
           -show_entries stream=nb_read_frames,r_frame_rate -of default=nw=1 /root/imx415.h264
   ```

## 六、为什么预览端不直接测端到端延迟

OpenCV 的 `VideoCapture` 只给解码后的图像，不暴露：

- H.264 SEI（板端可以把采集墙钟塞进去）；
- FLV 时间戳 / 流内 PTS（可以算出排队时间）。

要测真正的玻璃到玻璃延迟，需要额外做（当前未实现）：

1. 板端在每帧 SEI 里写 `CLOCK_REALTIME` 微秒，或首帧打印 `pts=0` 对应的墙钟；
2. 预览端改用 PyAV 读流，取出 SEI/PTS；
3. 板端与 PC 用 NTP 对时（或做一次基线校准）。

这条路线会引入新依赖和码流改动，属于后续阶段。

## 七、代码位置

| 文件 | 作用 |
|---|---|
| `inc/pipeline_stats.h` / `src/pipeline_stats.c` | 计数窗口、延迟采样、1 Hz 打印、退出汇总 |
| `inc/pipeline.h` / `src/pipeline.c` | `pipeline_t` 内嵌统计结构；`pipeline_collect_stats()` 生成计数快照 |
| `src/thread_encode.c` | 记录 `cap2enc` |
| `src/thread_consume.c` | 记录 `cap2file` / `cap2mux`、每秒 tick、落盘失败降级 |
| `src/main.c` | `-o/-r/-or` 解析、统计初始化与退出汇总 |
| `scripts/rtmp_preview/preview_rtmp.py` | 解码 fps、显示 fps、状态栏与终端输出 |
