# 三线程采集 / 编码 / 消费流水线改造记录

> 工程：`mediaCam` 主线（RK3568 + IMX415 + RGA + MPP）
> 改造目标：把单线程 `DQBUF → RGA → MPP → fwrite → QBUF` 拆成三线程 + 双环形缓冲区
> 记录时间：2026-10-31

---

## 一、改造背景

改造前，主流程是一条单线程直线：

```text
main
 └─ encode_frame()
     └─ for (每一帧)
          DQBUF
          → RGA 4K 转 1080p
          → mpp_encoder_encode()
              → encode_put_frame
              → encode_get_packet
              → fwrite 到 enc->fp_out
          → QBUF
```

这条链路能跑通，但存在几个问题：

1. **MPP 编码器直接持有输出文件**：`mpp_encoder_init` 里 `fopen`，`mpp_encoder_encode` 里 `fwrite`，`mpp_encoder_deinit` 里 `fclose`。编码和“写盘”耦合在一起，后面要加网络发送、分段录制、推流都很别扭。
2. **采集、编码、消费串行**：写文件或后续网络一旦变慢，会直接卡住 RGA 和 DQBUF，没有缓冲余量。
3. **`encode_frame()` 职责过重**：V4L2、RGA、MPP、文件 I/O 全在一个函数里，参数 `use_dmaheap` 还把分配方式混进主流程，不利于扩展。
4. **H.264 是变长码流**：如果只是把 MPP 输出塞进字节流缓冲区，消费端无法知道每个包的边界，必须补记录头。

改造目标：

- 用两个环形缓冲区把三个阶段解耦；
- 三个线程都在 `main` 里创建，线程逻辑分别放在独立 `.c` 文件；
- 编码器只负责编码，不再碰文件；
- 保存逻辑收敛到 `utils/` 下的通用函数；
- `ringbuffer.c/.h` 也移动到 `utils/`，作为通用组件复用。

## 二、改造后架构

```text
                       thread_capture                 thread_encode                    thread_consume
                       ┌──────────────┐               ┌──────────────┐                 ┌──────────────┐
V4L2 DQBUF ──RGA──>    │  frame_rb    │ ──copy──>     │  MppBuffer   │ ──MPP编码──>    │  packet_rb   │ ──save──> 指定路径
   ↑                   │  NV12 帧     │               │  1080p NV12  │                 │  H.264 包    │
   └────── QBUF ────────┴──────────────┘               └──────────────┘                 └──────────────┘
```

三个线程职责：

| 线程 | 文件 | 职责 | 阻塞点 |
| --- | --- | --- | --- |
| `thread_capture` | `src/thread_capture.c` | `poll` 等帧 → `DQBUF` → RGA → 写 `frame_rb` → `QBUF` | `poll`、`frame_rb` 写满 |
| `thread_encode` | `src/thread_encode.c` | 读 `frame_rb` → 拷入 MppBuffer → MPP 编码 → 取包 → 写 `packet_rb` | `frame_rb` 无数据、MPP 编码、`packet_rb` 写满 |
| `thread_consume` | `src/thread_consume.c` | 读 `packet_rb` → 调用保存组件写文件 | `packet_rb` 无数据、磁盘写入 |

`main` 只负责：初始化摄像头/环/编码器 → 创建三个线程 → 按 capture、encode、consume 顺序 join → 清理资源。

## 三、两个环形缓冲区与记录协议

两个环都是 `utils/ringbuffer.c` 里的 `struct ringbuffer`，只是容量和存放内容不同。

### 3.1 记录结构

定义在 `inc/pipeline.h`：

```c
typedef struct {
    uint32_t magic;       /* FRAME_MAGIC */
    uint32_t size;        /* NV12 字节数 */
    uint32_t width;
    uint32_t height;
    uint64_t pts_us;      /* V4L2 时间戳，后续 MP4/网络需要 */
    uint32_t seq;
    uint32_t reserved;
} frame_record_t;

typedef struct {
    uint32_t magic;       /* PACKET_MAGIC */
    uint32_t size;        /* H.264 包字节数 */
    uint64_t pts_us;
    uint32_t seq;
    uint32_t flags;       /* HEADER / EOS / 预留 KEY */
    uint32_t reserved;
} packet_record_t;
```

每条记录在环里的布局都是：

```text
[frame_record_t][NV12 数据]
[packet_record_t][H.264 数据]
```

记录头是必需的：H.264 包长度不固定，消费线程要先读头里的 `size`，才知道后面该读多少字节；同时 `pts_us/seq` 可以一路透传到后续的 MP4 封装或网络发送。

包标志：

```c
#define PKT_FLAG_HEADER 0x01u   /* SPS/PPS 头包 */
#define PKT_FLAG_EOS    0x02u   /* 编码结束包 */
#define PKT_FLAG_KEY    0x04u   /* 预留，首版未填 */
```

### 3.2 容量与超时

| 项目 | 值 | 说明 |
| --- | --- | --- |
| 编码分辨率 | 1920×1080 | RGA 输出 / MPP 输入 |
| 单帧 NV12 | 3,110,400 B | 1920×1080×1.5 |
| `frame_rb` | 4 帧，约 12.4 MB | 抵抗编码抖动，约 160 ms 缓冲 |
| `packet_rb` | 8 MB | H.264 包变长，留足余量 |
| 单包上限 | 4 MB | 超过按异常处理 |
| 写环超时 | 1000 ms | 超时视为链路卡死 |
| 读环轮询 | 100 ms | 用于及时检查 done/fatal |
| 读 payload 超时 | 1000 ms | 头已读到，体不应长期缺失 |

两个环都是**单生产者 + 单消费者**，不开 `overwrite`，环满时阻塞生产者形成背压。

### 3.3 记录读写封装

`src/pipeline.c` 提供：

```c
int pipeline_write_frame(...);
int pipeline_read_frame(...);
int pipeline_write_packet(...);
int pipeline_read_packet(...);
```

返回值约定：

- `1`：读到一条完整记录；
- `0`：读超时，调用方回去检查 `capture_done/encode_done/fatal`；
- `-1`：记录损坏、长度异常或写环失败。

这样三个线程里不需要重复处理 magic、长度校验和包头/包体两次写入。

## 四、三个线程的实现要点

### 4.1 thread_capture

流程：

```text
poll(dev->fd, 100ms)
  ↓ 有帧
DQBUF
  ↓
rga_resize_nv12(4K NV12 → 1080p NV12)
  ↓
dma_buf_cpu_begin(RGA 输出 fd, 只读)
pipeline_write_frame(frame_rb, NV12 数据, pts, seq)
dma_buf_cpu_end()
  ↓
QBUF
```

关键点：

1. **`DQBUF` 成功后无论 RGA/写环是否成功，都必须 `QBUF`**。代码里用统一的 `requeue` 路径保证这一点，否则 V4L2 buffer 会越来越少，最后采集停住。
2. 用 `poll()` 等帧，而不是无限阻塞 `DQBUF`，这样 Ctrl-C 后最多 100 ms 就能检查到停止标志。
3. RGA 输出是 dma-buf，CPU 读之前用 `dma_buf_cpu_begin/end` 包住，避免缓存不一致。
4. 帧记录里的 `pts_us` 来自 `buf.timestamp`，`seq` 来自 `buf.sequence`。

### 4.2 thread_encode

流程：

```text
取 SPS/PPS
  ↓
作为 PKT_FLAG_HEADER 包写入 packet_rb
  ↓
while (!fatal && !(capture_done && frame_rb 为空)):
    读 frame_record_t + NV12
    拷入 MppBuffer（CPU 写，前后 dma_buf_cpu_begin/end）
    mpp_encoder_encode(enc, enc_buf)
    循环取 packet，写入 packet_rb
  ↓
mpp_encoder_send_eos()
  ↓
继续取包直到 EOS，全部写入 packet_rb
  ↓
encode_done = 1
```

关键点：

1. **SPS/PPS 也走环形缓冲区**。`mpp_encoder_init` 只把头拷贝到 `enc->header`，编码线程把它作为第一条包写进 `packet_rb`，消费线程按顺序写盘，文件开头仍然是合法的 H.264 头。
2. `enc_buf` 只有一块，必须确认当前帧的 packet 已经取到，才能覆盖它进入下一帧；否则 MPP 可能还在读旧 buffer。代码里取不到 packet 会直接按致命错误停机。
3. 每帧 `encode_put_frame` 后至少取到一个包；排空 `frame_rb` 后再发 EOS，把编码器内部缓存的帧也吐干净。
4. 取包后先 `pipeline_write_packet` 拷贝进环，再 `mpp_packet_deinit`，避免包内存失效。

### 4.3 thread_consume

流程：

```text
file_saver_open(output_path, "wb")
  ↓
while (!fatal && !(encode_done && packet_rb 为空)):
    读 packet_record_t + payload
    file_saver_write(payload, size)
    每 100 个包 flush 一次
  ↓
file_saver_close()
```

关键点：

1. 输出路径来自 `pipeline->output_path`，由 `main` 从命令行参数或默认值 `/root/imx415.h264` 写入。
2. 保存逻辑集中在 `utils/save_utils.c`，消费线程只负责“从环里取包 + 调保存接口”。后续要加网络发送，只需要替换这一层，采集和编码不用动。
3. 写文件失败置 `fatal` 并停环，避免生产者一直等一个已经退出的消费者。

## 五、MPP 编码器接口优化

改造前后对比：

| 接口 | 改造前 | 改造后 |
| --- | --- | --- |
| `mpp_encoder_init` | 接收输出路径，内部 `fopen` | 只接收宽/高/fps，不碰文件 |
| `mpp_encoder_encode` | put frame + 取包 + `fwrite` | 只 `encode_put_frame` |
| 取包 | 藏在 `mpp_encoder_encode` 内部 | 新增 `mpp_encoder_get_packet` |
| EOS | 藏在 `mpp_encoder_deinit` 里并写文件 | 新增 `mpp_encoder_send_eos`，由编码线程显式调用 |
| 析构 | `fclose(fp_out)` + EOS 冲刷 | 只释放 MPP 实例和 SPS/PPS 缓存 |
| SPS/PPS | init 时直接写文件 | 缓存在 `MppEncoder.header`，作为头包进环 |

改造后的接口：

```c
int  mpp_encoder_init(MppEncoder *enc, int width, int height, int fps);
int  mpp_encoder_get_header(MppEncoder *enc, const unsigned char **data, size_t *len);
int  mpp_encoder_encode(MppEncoder *enc, MppBuffer buf);
int  mpp_encoder_get_packet(MppEncoder *enc, MppPacket *packet, int timeout_ms);
int  mpp_encoder_send_eos(MppEncoder *enc);
void mpp_encoder_deinit(MppEncoder *enc);
```

这样编码模块不再依赖 `FILE *`，也不再决定码流去哪里，职责更单一。

## 七、启动、停机与错误处理

### 7.1 启动顺序

1. 打开摄像头，设置格式、申请/映射 buffer、入队、开流；
2. 预热若干帧等 AE 稳定；
3. 初始化 `frame_rb`、`packet_rb`；
4. 初始化 MPP 编码器，缓存 SPS/PPS；
5. 申请 RGA 输出和 MPP 输入两块 MppBuffer；
6. 创建 capture、encode、consume 三个线程。

### 7.2 正常停机

- `capture` 到达目标帧数后置 `capture_done`；
- `encode` 排空 `frame_rb`，发 EOS，排空编码器，置 `encode_done`；
- `consume` 排空 `packet_rb`，关闭文件；
- `main` 依次 join 三个线程，释放 buffer/编码器/环，`stream_off`、`close_device`。

### 7.3 异常与 Ctrl-C

- `SIGINT/SIGTERM` 的信号处理函数只置 `g_pipeline_stop`，不调用任何非异步信号安全函数；
- 采集线程每轮检查该标志，并通过 `poll` 超时和写环超时保证能退出；
- 任一环节出错置 `pipeline->fatal`，并调用 `pipeline_abort()`：对两个环 `rb_stop()`，唤醒所有阻塞的读写；
- 其他线程看到 `fatal` 后停止排空并退出；
- 不使用 `pthread_cancel`，避免 MPP/RGA 资源处于半初始化状态。

最后保留 `_exit(0)`，绕过 `librockchip_mpp` 退出阶段约 14 秒的全局清理；消费线程已经 `fclose`，H.264 文件是完整的。

## 十、设计取舍与后续优化

### 10.1 为什么 ringbuffer 里存 NV12 字节，而不是 fd

RGA 输出是 dma-buf fd，MPP 输入要求 `MppBuffer`，而通用环形缓冲区是普通内存。首版选择：

```text
RGA dma-buf → memcpy 到 frame_rb → memcpy 到 MppBuffer
```

每帧 3.1 MB，两次拷贝在 25 fps 下约 155 MB/s，预计每帧 2~5 ms，仍在 40 ms 帧预算内。好处是逻辑简单、环里是自包含数据，消费端不依赖 buffer 生命周期。

如果后续实测 dma-buf 的 CPU 访问成为瓶颈，可以升级为“fd 描述符环”：

- 环里只放 `{fd, size, pts, seq}`；
- capture 用 RGA 直接写 N 块 dma-buf；
- encode 直接 import 并编码；
- 编码完成后再把块还给 capture 的空闲池。

这样能省掉两次大拷贝，但需要额外的 buffer 池和引用计数，复杂度更高。

### 10.2 为什么写环超时按致命处理

`rb_write_block` 超时可能已经写入了半条记录。首版不做“半记录回滚/续写”，而是：

- 正常运行时给 1 秒超时；
- 超时说明编码/消费链路已经卡死；
- 置 `fatal`、`rb_stop`，整体停机。

这样不会让消费线程把半条记录当成完整包头继续解析。

### 10.3 后续可做

1. **零拷贝 fd 环**：省掉两次 NV12 拷贝。
2. **sink 抽象**：把 `file_saver` 抽成 `sink` 接口，实现文件/网络/内存多种消费端。
3. **分辨率与帧率可配置**：目前 4K→1080p、25 fps 写死在 `pipeline.h` 和 `main.c`。
4. **运行统计**：capture/encode/consume 各自帧率、环水位、丢帧/超时计数。
5. **优雅退出**：当前用 `_exit` 规避 MPP 退出清理，产品化常驻进程需要重新设计退出路径。
